OpenJev, explained

A small open model that reads a situation and a list of questions, then answers all of them in one pass, with honest probabilities.

Last updated: 2026-11-19 (date of the newest commit in the git log). All facts come from the repo notes. Anything I could not confirm is marked uncertain.

What OpenJev is

OpenJev is an open copy of the Jev "System One" model from TypeSafe AI. It is a causal encoder. That means it is a pretrained decoder LLM that keeps its causal mask but no longer writes text.

You give it a state (a text) and typed questions. Small heads read the hidden states at special tokens. So it answers every question in one forward pass. Each answer is a calibrated probability.

The backbone is Gemma 4 E2B. The attention mask follows the Prism idea from Sarvam. Training uses LoRA, first SFT and then RL.

The model reads once. The flag head turns each flag token into a number.

The goal

Match the Jev request and answer format exactly. Train it on decision data. Make the probabilities calibrated: when it says 70%, it should be right about 70% of the time. Then serve it behind the same API shape as Jev.

Hard rule from CLAUDE.md: the public format follows Jev, no matter what. Never add a public type or field that Jev does not have. Internal details (template tokens, heads, losses) may change, because they never appear in the request or answer.

The model

Gemma 4 E2B with a flag head, used as an encoder that never generates text.

Gemma 4 E2B

Gemma 4 E2B is a Google model. The "E" means effective. The repo notes call it 2.3B effective parameters. The full text part is much larger, because of PLE (see below).

  • Measured on the meta device: the E2B text part has 4.63B parameters, of which PLE is 2.35B (TASKS, 2026-11-19).
  • With the PLE table off the GPU, E2B weights take 4.6 GB in fp16.
  • The model card, as quoted in the research notes: 35 layers, a 512-token sliding window, 128K context, Apache 2.0.
  • OpenJev loads only the text decoder. The vision and audio towers are dropped.

The request and answer format

Three question types. This is the Jev format, copied exactly.

TypeCriteria in the requestAnswer
noul{"true": desc, "false": desc}{"type":"noul","noul": p}
choiceoptions: {option: desc}, 2 to 255choice, probabilities, confidence
scoreordered levels: ["level0","level1",...], 2 or morescore, legend, probabilities, confidence
{"state": "...", "questions": {"<name>": {"type": "noul|choice|score",
                                         "instructions": "...", "criteria": ...}}}
If the data does not fit, adapt the data, not the format. A continuous number becomes ordered score levels (openjev.data.bucket). Several options true at once become one noul question per option.

The flag head

The template puts a special <|flag|> token after each option. The flag head is one linear layer, nn.Linear(hidden, 1). It gives one true/false logit at each flag token.

For a question, a softmax over its flags gives the probabilities. One gather reads all flags of all questions at once, so one forward pass answers everything. Confidence follows Jev. The research notes quote the formula (p_max - 1/n) / (1 - 1/n) as Jev's. uncertain That is the research notes' reading of Jev, not code I checked in the serve path.

PLE: Per-Layer Embeddings, and why it is big

A normal LLM has one embedding table. Gemma 4 E2B also has PLE. Each token id looks up an extra vector for every layer, and each layer adds its vector into the hidden state. This gives each layer token-specific information.

The PLE table is embed_tokens_per_layer. It has 262,144 rows (one per token id). Each row holds the vectors for all layers. The notes record about 18 KB per token, and 4.70 GB for the full table in fp16. uncertain My own check: 18 KB fits 35 layers x 256 numbers x 2 bytes. The notes do not state that split.

That is why E2B is "2.3B effective" but 4.63B in total. PLE rows are a lookup, not a matrix multiply, so they cost memory but little compute.

Two consequences. We keep the PLE table on the CPU (--ple-cpu) to save 4.7 GB of GPU memory. And lookups from the CPU cost time, which drives the speed work. See Speed work.

GQA and KV sharing

GQA (grouped-query attention). Many query heads share fewer key/value heads. Query head h uses KV head h // (H / H_kv). This makes the KV tensors smaller. Our custom attention code must handle it without copying K/V.

KV sharing. Some late layers do not compute their own keys and values. They reuse the K/V of an earlier layer. Gemma 4 sets this with num_kv_shared_layers. The attention backends simply receive the shared tensors.

Sliding and global layers

Gemma 4 mixes two layer kinds. Sliding layers look only at tokens within a window (512 per the model card). Global layers look at all tokens. The head size differs too: 256 for sliding, 512 for global (SPEED_LOG). I did not find the exact sliding-to-global ratio in the notes. uncertain

Prism builds two masks, one for each kind. The sliding mask is the Prism mask limited to |pos_q - pos_k| < window, measured on Prism position ids.

The Prism mask

Attention rules that let all options of a question be scored together, and in any order, in one pass.

The original Sarvam idea

Sarvam Prism (blog, 2026-11-03) changes only the attention mask of a decoder LLM. Four rules (from openjev/prism.py):

  1. The state and question block is read in both directions.
  2. Each option sees that block and itself, never the other options.
  3. Every option starts from the same position id.
  4. Only the answer token sees everything, so options are compared there.
Do not confuse it with Prism-1 (NTU, arXiv 2610.22066). It is a different design with no token after the option blocks. The two designs are unrelated as far as the research notes could tell. uncertain Whether the authors are connected is unverified.

Our version

OpenJev already has a <|flag|> token after each option. The flag plays the role of Prism's answer token. Each option is one segment: its tokens plus its flag.

  • The shared block sees only itself.
  • An option token sees the shared block and its own segment.
  • A flag also sees the sibling flags of its question. This is how options get compared.
  • Padding rows see only themselves, so no row is empty and no NaN appears.

The OJ-080 bug

Bug In v8 the per-source validation accuracy was identical at SFT 30, SFT 60 and RL 20 (for example clinc .4898, banking77 .00). The model gave near-uniform output (val NLL 2.13 against 2.31 for uniform) and the argmax never moved.

Cause. The old mask let a flag see every option token of its question. So all flags of one question attended to the same keys. All flags also share one embedding. They could differ only by their own position. Options of equal token length got exactly the same logit.

Fix. A flag sees the shared block, its own option, and the sibling flags (not sibling option tokens). That breaks the tie but keeps the comparison. Commit 6df0efe. A second bug was fixed in the same commit: evaluate() zipped labelled views against all questions, so the source shifted after a None label. The fix is view_sources().

Ruled out first (OJ-080 log): the optimizer and GradScaler, the learning rate, and frozen weights. LoRA B, the head and template_delta all changed.

Consequence. The v8 checkpoints came from the broken mask. SFT must be retrained from scratch.

Why shared positions give option-order invariance

Every option of a question starts at the same position id. Options do not see each other's tokens. So moving option B before option A in the text changes where tokens sit in the sequence, but not their position ids or what they can see. The computation for each option is the same. Only the order of the outputs changes.

Sarvam reports 0 changes in 2,000 shuffled questions (blog, as quoted in the research notes). OpenJev has an option-order invariance test in tests/test_prism.py (TASKS, 2026-11-18). Flags see each other, but only as a set, so the sibling-flag link is symmetric.

uncertain Prism-1 reports that options attending to each other cost 3 to 5 points and break the Luce choice axiom in their design. OJ-065 plans an A/B of isolated flags (Prism-1 style) against siblings (Sarvam style), with an option-order flip-rate metric. We have no OpenJev result for it yet.

Training recipe

Short SFT first. Then RL that sharpens and calibrates.

Stage 1: SFT

Cross-entropy over the flags of each question (--algo sft). It gives the model the task, the label format and a sane option distribution. LoRA trains on q, k, v, o, gate, up and down projections. The embedding matrix is frozen. Seven template tokens get an fp32 template_delta. Trainable weights are fp32.

Stage 2: RL

Two algorithms, same script:

  • exact - exact policy gradient. A decision has a small known action set. So the expected reward E_p[r] = sum_i p_i r_i is computed over all options, with no sampling. The gradient has zero sampling variance.
  • grpo - GRPO with Dr. GRPO details: sample G options, group-mean baseline, no std normalization, PPO clip, k3 KL to the reference. Use it only if the reward needs a sampled action.

Rewards (--reward): acc, graded (for score questions, 1 - |i - y| / (K - 1)) and brier.

Brier reward (exact only): r(p) = 1 - sum_i (p_i - 1[i = y])^2. It is a proper scoring rule over the whole distribution. So RL does not push every answer to probability 1.

Extra terms: --lam-cal times soft ECE and --lam-kl times KL(p || p_ref). The reference is the same backbone with the adapter off, so it costs no extra GPU memory. The loss is: proper score + lam_cal x soft-ECE + lam_kl x KL (+ a contrast term in rlcd_train.py). Soft ECE is computed per question type, then averaged.

For the plain-language story of KL and ECE with live demos, read the KL and soft ECE explainer.

Why not direct RL?

The research summary (docs/research/sft-vs-rl) recommends SFT then RL with a short SFT. Confidence: moderate. Main reasons:

  • RL cannot add capability beyond what the model can already sample (DeepSeekMath, Yue et al.). SFT supplies knowledge and format.
  • Small models: R1 reports distillation beats RL on small models. In the GTA paper, pure GRPO scored below SFT on 3-4B classification. The hybrid gained about 0.5 to 1 point over SFT.
  • RL fails when the start does not follow the format (Chu et al.).
  • Binary-reward RL hurts calibration. A Brier reward fixed it at equal accuracy in RLCR (ECE 0.37 to 0.03), but only at 7B.
  • Expect modest accuracy gains, larger calibration gains. Evaluate out of distribution and with Brier and ECE.
uncertain Gaps the research names: nothing tests an option-scoring head with an RL reward directly. How RL gain changes with size from 0.5B to 10B is unknown. Direct RL at 2B is untested here. Gemma E2B-it may follow the format already, so direct RL could work.

Speed work

Training costs about 4.5 seconds per sample on a T4. Everything here tries to lower that without losing quality.

The baseline

RunSetups/stepSamples/steps/sample
v71 x T4, bs 4 x accum 8, grad-ckpt, padded, max state 1024about 14032about 4.4
v8 short1 x T4, bs 4 x accum 2, sameabout 358about 4.5

The cost per sample is the same at both batch sizes. So the cost is per sample, not per step. The notes estimate the hardware limit at about 1 s/sample. That estimate uses 6 x N x T FLOPs for about 1.9B non-PLE parameters and about 1000 tokens, plus about 33% for checkpoint recompute, at about 15 TFLOP/s of effective T4 fp16. uncertain It is an estimate, not a measurement.

Round-1 best is Optuna trial 3: 1.05x. It was measured under the old mask and possibly emulated bf16.

Why it is slow

  1. The math attention kernel. The memory-efficient SDPA kernel rejects our float mask for head dim 256/512 on sm75 ("No available kernel"). The fallback is the math kernel. It builds the full T x T score matrix, which is slow and memory-hungry.
  2. Padding. Mixed batches hold 11-token and 1000-token samples. Short ones are padded to the longest.
  3. Emulated bf16. The T4 has no native bf16. Early runs used emulated bf16 by mistake (see the failure log).
  4. Other overhead. The Round-1 note says about 120 tokens/s is roughly 10% of what a T4 should do, so a large overhead is hidden. A profile trial (OJ-082) is meant to name it. uncertain No profile result is logged yet.
  5. Gradient checkpointing costs about 33% more compute. E2B uses about 7 of 15 GB, so it may not be needed (OJ-073).

The micro-batch 8, global batch 32 decision

Batch size changed both speed and the optimization itself: gradient noise scales with 1/batch and the best learning rate scales with batch (Goyal et al.; McCandlish et al.). It also confused the quality guard. So bs left the search. Every trial now uses micro-batch 8 and accumulation 4, so the global batch is 32.

  • The user fixed the idea. Claude chose 8 over 16 because 16 likely runs out of memory.
  • A config that runs out of memory at micro-batch 8 is pruned as infeasible_at_mb8. It is never retried smaller. A memory-saving trick earns credit only by making a config fit at 8.
  • The round baseline records whether micro-batch 16 would fit (info only).

Compact PLE and the hot/cold idea

Why not store PLE output per token? It would need about 3.6 TB (18 KB per token x about 200M tokens).

Compact table (OJ-085). Keep only the rows of token ids that occur in the data, and remap ids for the PLE lookup. It is exact. Measured with the Gemma tokenizer plus 7 template tokens:

MeasurementValue
Distinct ids in train + val + test (max state 2048)157,146 (157,068 at 1024)
Compact fp16 table2.82 GB, which is 0.60 of the full 4.70 GB
Tokens in total / in trainabout 190M / 161M
Val ids not in train / test ids not in train861 / 812
helpsteer3 alone155,235 ids; other sources add only about 2k

The saving is only 40%, because helpsteer3 covers most of the vocabulary. The original estimate of about 1.1 GB (30-60k ids) did not hold.

Hot/cold split (OJ-085b). Keep on the GPU only the ids that cover about 99% of token occurrences. Look up the rare ids on the CPU. First step: measure the coverage curve. It is a plan, not a result. The goal is PLE-on-GPU speed with PLE-on-CPU memory.

The Optuna loop

A search for the fastest training setup, run in small steps because Kaggle cannot be driven live.

How ask/tell works with Kaggle

Optuna normally calls your function directly. Here the function runs on a Kaggle GPU in a different place. So we split the loop into steps you run by hand, using tools/optuna_loop.py. This is called ask/tell: ask for configs, run them elsewhere, tell Optuna the results.

The study lives in SQLite under runs/optuna. The sampler is TPE (multivariate) with a "constant liar" so several trials can be proposed before results return. Trial 0 is the baseline. A trial is PRUNED (not failed) on OOM, NaN, no kernel, or a quality-guard failure. Kernel id: openjev-prism-optuna (Kaggle env PROFILE=optuna). One model load serves a whole reload group, because a load takes about 7 minutes.

The fair-experiment rules

  • Fixed micro-batch. 8 x accum 4 = 32. No batch-size confounding.
  • Frozen trial stream. The same 640 records, stratified by source with the mixture weights (its sha is stored in trial_stream_sha). Every trial times the same sequence lengths. Each trial uses 1 warm-up step and 4 timed optimizer steps.
  • Quality guard. A fixed probe set. The probe-loss drop after the same warm-up step must stay close to the round baseline. The frozen probe set has 8 records (sha 8296cda54dcd650c).
  • Periodic validation. Every 30 trials and at round end, PROFILE=optuna_validate trains the best config and the baseline for 150 steps on a frozen 400-record val set (stratified by type and option-count bucket; sha 1de87bf5...). Accept a speedup only if val NLL is within +0.05 of base and accuracy is no worse than -1 point. With about 400 records, the accuracy standard error is about 2 points.
  • Self-describing trials. All fixed conditions are in the study note and trial attrs, with a fixed_conditions_version.
  • Per-round baseline. The "vs base" number uses only the current round's baseline.

How ideas become search dimensions

  1. Write the idea in tools/search_space.yaml as a planned placeholder (not sampled). The current file lists 6 implemented dims and 9 planned ones at the first snapshot. Round 2 added attn_backend, profile and dtype.
  2. Implement it in bench_trials.py or train_prism.py behind a flag, with a correctness test first (for example, logits equal the old path).
  3. Mark it a dim. Choose whether it needs a model reload (a "reload group").
  4. Run it alone first with propose --enqueue-json (exact configs, missing keys use the yaml defaults), then let TPE combine it with others.
  5. Check quality with the 150-step validation before adopting.

Planned but not implemented (not sampled): option_subsample_k, packing, pack_len, ddp, fp16_compress_hook, bucket_cap_mb, quant, torch_compile, dataloader_workers.

Hardware and the 50-hour plan

A T4 is slow and small. The plan is to chain GPU and TPU sessions toward about 50 hours of training.

T4 limits

  • Kaggle gives 2 x T4. Each has 16 GB nominal (14.56 GiB usable in one OOM message). The link is PCIe, no NVLink.
  • The T4 (sm75) has fp16 but no native bf16. Use fp16 with a GradScaler.
  • A session is capped at about 12 h.
  • The model fits on one GPU and only LoRA trains. So DDP (two copies) fits, and FSDP or pipeline splits add only communication.
uncertain Kaggle quotas of about 30 h GPU and about 20 h TPU per week, and session caps of 12 h (GPU) and about 9 h (TPU), come only from community sources. The official Kaggle pages could not be read.

The TPU: memory per chip versus total

Kaggle offers a TPU v5e-8: 8 chips. Each chip has 16 GiB of HBM and 197 bf16 TFLOP/s. So the total is 8 x 16 GiB, but each chip has only 16 GiB, the same as a T4. TPUs have native bf16.

Data parallel buys speed, not sequence length. Sharding frees memory (about 8 GB per chip, per the fork's estimate) for longer sequences or bigger micro-batches. With only 24M LoRA parameters training, the gain comes from sharding the frozen 4.6 GB weights and the 4.7 GB PLE table, plus activations.

uncertain The multi-chip SPMD mesh is implemented in the fork but untested on a real TPU. The "about 8 GB freed per chip" figure is an estimate.

Decision (2026-11-19, the fork's memo, status decided): option (a). torch_xla 2.9 is pinned for the TPU now. TorchTPU is the planned swap target, but its official page names only v6e and TPU7x. Whether it supports Kaggle's v5e is unverified. One module, openjev/backend.py, holds every device call so the swap touches one file. Revisit if torch_xla 2.9 cannot run HF Gemma 4 on Kaggle's v5e image, or if recompiles inside HF code cannot be removed. Then try TorchTPU, and only then JAX.

Static shapes. XLA compiles one graph per shape. The fork uses length buckets 512, 768, 1024, 1152, 2048, 2560 from measured lengths. For example, helpsteer3 samples are 1103 to 1122 tokens at a 1024 cap. A 1152 bucket fits them. At a 1024 cap helpsteer3 is cut 37.7%. At 2048 only 0.07%.

The fork at ~/openjev-xla

  • Goal: about 50 h of training. The plan is Kaggle GPU about 30 h plus TPU about 20 h per week, chained sessions (quota numbers unverified).
  • Own study openjev-xla-v1, kept apart from the GPU speed study.

Glossary

Brier score
Mean squared error between predicted probabilities and the one-hot truth. A proper scoring rule. Our RL reward is 1 minus it.
Causal encoder
A decoder LLM that keeps its causal mask but is read for hidden states, not for generated text.
CE
Cross-entropy, the SFT loss.
DDP
Distributed Data Parallel. One model copy per GPU, gradients averaged.
ECE
Expected Calibration Error. How far confidence is from accuracy, averaged over confidence bins. We report 15-bin ECE. Soft ECE is a differentiable version used in training.
EMD
Earth Mover's Distance. Used with cross-entropy as the ordinal loss for score questions.
Flag
The special token after each option. The flag head reads it.
FSDP
Fully Sharded Data Parallel. Splits weights, gradients and optimizer state across devices. Rejected for the T4s.
GQA
Grouped-query attention. Several query heads share one key/value head.
GRPO
Group Relative Policy Optimization. RL that uses the mean reward of a sampled group as the baseline. We use the Dr. GRPO variant.
GradScaler
Scales the loss in fp16 so small gradients do not underflow.
HBM
High-bandwidth memory, the on-chip memory of a TPU. 16 GiB per v5e chip.
Jev
TypeSafe AI's System One decision model. We copy its request and answer format.
KL
Kullback-Leibler divergence. Measures how far the new policy has drifted from the reference. Used as a penalty.
KV sharing
Late layers reuse the keys and values of an earlier layer.
LoRA
Low-Rank Adaptation. Train small low-rank matrices instead of all weights (rank 16 here; about 24M parameters on E2B).
NCCL
NVIDIA's GPU communication library, used by DDP.
NLL
Negative log-likelihood of the correct answer. Lower is better. Uniform over our options is about 2.31 in v8.
noul, choice, score
The three Jev question types: true or false, pick one option, pick an ordered level.
OOM
Out of memory.
Optuna
A hyperparameter search library. We use its ask/tell mode.
PEFT
Parameter-Efficient Fine-Tuning library that provides LoRA.
PLE
Per-Layer Embeddings. Extra per-token vectors for every layer in Gemma 4 E2B. Large lookup table.
PPO
Proximal Policy Optimization. Its clipping idea is used in GRPO here.
Prism
Sarvam's attention-mask design for scoring options. Also a name of a separate NTU paper (Prism-1).
RLCD
The name used in the repo for the RL stage with calibration (proper score + soft ECE + KL + contrast).
RoPE
Rotary position embedding. Positions enter through it.
SDPA
Scaled dot-product attention. PyTorch's attention function with several kernels.
SFT
Supervised fine-tuning.
sm75
The T4's CUDA compute capability (7.5). No native bf16.
SPMD
Single Program, Multiple Data. One program, tensors sharded by annotation. How XLA does multi-chip here.
TorchTPU
Google's successor to PyTorch/XLA. v5e support unverified.
TPE
Tree-structured Parzen Estimator. Optuna's default sampler.
TPU v5e-8
Kaggle's TPU: 8 chips with 16 GiB each.
XLA
Accelerated Linear Algebra. A compiler used for TPUs. It needs fixed shapes.
