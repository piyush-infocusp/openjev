# OpenJev speed experiments (Optuna)

Generated by `tools/optuna_loop.py report` from `study.db` (study `openjev-speed-v2`); the legacy study `LEGACY-r1-r2 (old mask, variable bs; not comparable)` (rounds 1-2, not comparable) is in the same db.
Objective: maximize training samples/s. Speedup is against the 4.5 s/sample v7/v8 baseline. Round 3: every trial runs at a FIXED micro-batch 8 and global batch 32 (grad_accum 4); a step is one optimizer step of 32 samples. 1 warm-up step(s), then 2 timed steps on the frozen trial stream (same records for every trial), from the same start weights. OOM at that micro-batch = pruned (infeasible_at_mb). The quality guard uses the probe loss after the warm-up steps (same steps and batches for every trial, so guards are comparable across trials). Rounds 1-2 did one optimizer step per micro-batch of a sampled `bs`; compare trials only within a round.

Trials: 23 total, 4 complete, 6 pruned (OOM / NaN / kernel / quality guard), 13 failed.

## Ideas not implemented yet (not sampled)

- `option_subsample_k` [0, 8, 16, 24]: OJ-072. Train on the gold option + k random negatives (0 = all options); clinc150 and banking77 templates shrink from ~1000 to ~200 tokens. Mikolov et al. 2013, arXiv:1310.4546.
- `packing` ['off', 'on']: OJ-060. Hierarchical packing with a doc-id block-diagonal mask, positions restart per request. Krell et al. 2021, arXiv:2107.02027.
- `pack_len` [1024, 2048]: OJ-060. Row length for packing (used only when packing is on).
- `ddp` ['off', 'on'] (reload): OJ-062. One process per T4 with torchrun (needs a torchrun launch, so a reload). Li et al. 2020, arXiv:2006.15704.
- `fp16_compress_hook` ['off', 'on'] (reload): OJ-078d. Halves the PCIe gradient traffic (small for 24M LoRA params). DDP comm hooks docs.
- `bucket_cap_mb` [25, 50] (reload): OJ-078b. DDP gradient bucket size; set at DDP wrap time. DDP docs.
- `quant` ['none', '8bit', 'nf4'] (reload): OJ-075. bitsandbytes 8-bit or 4-bit nf4 base weights (QLoRA). Less memory, but dequantization costs time. Dettmers et al. 2023, arXiv:2305.14314; 2022, arXiv:2208.07339.
- `torch_compile` ['off', 'on']: OJ-079. torch.compile(mode=default) with PEFT + float mask; keep only if stable. Ansel et al. 2024 (PyTorch 2), ASPLOS.
- `dataloader_workers` [0, 1, 2]: OJ-076. Tokenize and collate in DataLoader workers with pin_memory and non_blocking copies. PyTorch data loading docs.

## Ideas (round 1 → round 2)

Round-1 facts: 2× T4 present; baseline 0.189 samples/s (5.3 s/sample), 101 tokens/s. `ple_cpu=0` trials reached 0.233 samples/s
(+23%) and 128 tokens/s, so the CPU PLE lookup costs time. `sdpa_backend=efficient` → "No available kernel" for all trials, so the
default path is the **math** kernel. No grad-ckpt + math → OOM at 13.9 GB. About 120 tokens/s is roughly 10% of what a T4 should
do for a 2B LoRA forward/backward, so a large overhead is still hidden.

1. **Profile one training step** (torch.profiler, CUDA + CPU, top-20 ops by self time). Hypothesis: a few non-matmul ops (mask
   build, math attention softmax, PLE CPU copy, Python collate) dominate. Expected: it names the next target directly.
   Reference: PyTorch profiler recipe, https://pytorch.org/tutorials/recipes/recipes/profiler_recipe.html
2. **Attention backend that accepts our mask on T4.** The memory-efficient SDPA kernel rejects this case, which may be Gemma 4's
   head dims (256 sliding, 512 global) on sm75. Candidates: FlexAttention with a block mask (memory O(T), compiled Triton kernel),
   or query-chunked math attention (lower peak memory, which may allow grad-ckpt off). Expected: lower memory and faster attention.
   References: FlexAttention, Dong et al. 2024, arXiv:2412.05496; PyTorch SDPA docs,
   https://pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html
3. **Keep the PLE table on the GPU when memory allows** (`ple_cpu=0`; peak 10–12 GB with grad-ckpt). Expected: +20% as measured.
   This needs no new code, so TPE should focus there.
4. **dtype (OJ-081).** `--dtype auto` chose bf16 on the T4 because `torch.cuda.is_bf16_supported()` counts emulated bf16;
   sm75 has no native bf16, so round 1 likely ran emulated bf16. Round 2 defaults to fp16 + GradScaler (`dtype` dim) and
   has its own baseline (yaml `round: 2`), since round 1's baseline also predates the OJ-080 mask fix.
5. **Fixed global batch + fixed micro-batch (round 3, new study `openjev-speed-v2`).** Hypothesis: `bs` was a poor
   Optuna dimension. It changed the samples per optimizer step, so it (a) dominated samples/s and the importances
   (larger batches pad more but amortize per-step overhead), (b) changed the optimization itself: the gradient noise
   scales with 1/batch and the best lr scales with the batch (Goyal et al. 2017, *Accurate, Large Minibatch SGD*,
   arXiv:1706.02677; McCandlish et al. 2018, *An Empirical Model of Large-Batch Training*, arXiv:1812.06162: the
   gradient noise scale sets how much a larger batch helps), and (c) confounded the quality guard, which compared the
   loss drop after 2 optimizer steps of 2 to 16 samples. Change: yaml study settings `micro_batch: 8` and
   `global_batch: 32` (grad_accum 4) for EVERY trial; one timed step = one optimizer step of 32 samples; samples/s =
   32 x steps / seconds. `bs` (and `dtype`, `ple_cpu`) are `sample: false`; bench ignores `bs` at a fixed
   micro-batch. A config that runs out of memory at micro-batch 8 is PRUNED as `infeasible_at_mb8` (never retried
   smaller): a memory-saving technique gets credit only by making a config feasible at 8. The round baseline records
   whether micro-batch 16 WOULD fit (study attr `mb16_fits_round_3`), only as information. Every trial trains on the
   same frozen trial stream (`optuna_loop.py freeze`: 640 record ids stratified by source with the mixture weights;
   sha in `trial_stream_sha`) for 1 warm-up step + 4 timed steps, so all trials time the same records.
   **Guards are now comparable across trials:** the quality guard compares the probe-loss drop after the same warm-up
   optimizer step(s), on the same 32-sample batches, against the round-3 baseline. Quality checkpoints
   (`validate-plan`, PROFILE=optuna_validate) train best vs baseline for 150 optimizer steps and compare val
   acc / nll / ece on a frozen, stratified ~400-record val set (accept if nll <= base + 0.05 and acc >= base - 1 pt;
   with ~400 records the acc standard error is ~2 pt). Expected: importances that show real techniques, and a TPE that
   no longer chases batch size. Open: `max_state_tokens` is still sampled and changes sequence lengths and quality the
   same way; `ple_cpu` is PENDING a paired test (enqueue the baseline with ple_cpu 0 and 1). Round 2 note: every r2
   trial ran ple_cpu=1 (sample: false dims were not written into trials.json, and train_prism defaults to 1).
