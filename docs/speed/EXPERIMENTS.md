# OpenJev speed experiments (Optuna)

Generated by `tools/optuna_loop.py report` from `study.db` (study `openjev-speed-v3`); the legacy study `LEGACY-r1-r2 (old mask, variable bs; not comparable)` (rounds 1-2, not comparable) is in the same db.
Objective: maximize training samples/s. Speedup is against the 4.5 s/sample v7/v8 baseline. Round 9: every trial runs at a FIXED micro-batch 8 and global batch 32 (grad_accum 4); a step is one optimizer step of 32 samples. 1 warm-up step(s), then 1 timed steps PER LENGTH BUCKET of the fixed bench set (objective = weighted samples/s), from the same start weights. OOM at that micro-batch = pruned (infeasible_at_mb). The quality guard uses the probe loss after the warm-up steps (same steps and batches for every trial, so guards are comparable across trials). Rounds 1-2 did one optimizer step per micro-batch of a sampled `bs`; compare trials only within a round.

Trials: 11 total, 8 complete, 3 pruned (OOM / NaN / kernel / quality guard), 0 failed.

## Ideas (round 1 → round 2)

Round-1 facts: 2× T4 present; baseline 0.189 samples/s (5.3 s/sample), 101 tokens/s. `ple_cpu=0` trials reached 0.233 samples/s
(+23%) and 128 tokens/s, so the CPU PLE lookup costs time. `sdpa_backend=efficient` → "No available kernel" for all trials, so the
default path is the **math** kernel. No grad-ckpt + math → OOM at 13.9 GB. About 120 tokens/s is roughly 10% of what a T4 should
do for a 2B LoRA forward/backward, so a large overhead is still hidden.

1. **Profile one training step** (torch.profiler, CUDA + CPU, top-20 ops by self time). Hypothesis: a few non-matmul ops (mask
   build, math attention softmax, PLE CPU copy, Python collate) dominate. Expected: it names the next target directly.
   Reference: PyTorch profiler recipe, https://pytorch.org/tutorials/recipes/recipes/profiler_recipe.html
2. **Attention backend that accepts our mask on T4.** The memory-efficient SDPA kernel rejects this case, which may be Gemma 4's
   head dims (256 sliding, 512 global) on sm75. Candidates: FlexAttention with a block mask (memory O(T), compiled Triton kernel),
   or query-chunked math attention (lower peak memory, which may allow grad-ckpt off). Expected: lower memory and faster attention.
   References: FlexAttention, Dong et al. 2024, arXiv:2412.05496; PyTorch SDPA docs,
   https://pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention.html
3. **Keep the PLE table on the GPU when memory allows** (`ple_cpu=0`; peak 10–12 GB with grad-ckpt). Expected: +20% as measured.
   This needs no new code, so TPE should focus there.
4. **dtype (OJ-081).** `--dtype auto` chose bf16 on the T4 because `torch.cuda.is_bf16_supported()` counts emulated bf16;
   sm75 has no native bf16, so round 1 likely ran emulated bf16. Round 2 defaults to fp16 + GradScaler (`dtype` dim) and
   has its own baseline (yaml `round: 2`), since round 1's baseline also predates the OJ-080 mask fix.
5. **Fixed global batch + fixed micro-batch (round 3, new study `openjev-speed-v2`).** Hypothesis: `bs` was a poor
   Optuna dimension. It changed the samples per optimizer step, so it (a) dominated samples/s and the importances
   (larger batches pad more but amortize per-step overhead), (b) changed the optimization itself: the gradient noise
   scales with 1/batch and the best lr scales with the batch (Goyal et al. 2017, *Accurate, Large Minibatch SGD*,
   arXiv:1706.02677; McCandlish et al. 2018, *An Empirical Model of Large-Batch Training*, arXiv:1812.06162: the
   gradient noise scale sets how much a larger batch helps), and (c) confounded the quality guard, which compared the
   loss drop after 2 optimizer steps of 2 to 16 samples. Change: yaml study settings `micro_batch: 8` and
   `global_batch: 32` (grad_accum 4) for EVERY trial; one timed step = one optimizer step of 32 samples; samples/s =
   32 x steps / seconds. `bs` (and `dtype`, `ple_cpu`) are `sample: false`; bench ignores `bs` at a fixed
   micro-batch. A config that runs out of memory at micro-batch 8 is PRUNED as `infeasible_at_mb8` (never retried
   smaller): a memory-saving technique gets credit only by making a config feasible at 8. The round baseline records
   whether micro-batch 16 WOULD fit (study attr `mb16_fits_round_3`), only as information. Every trial trains on the
   same frozen trial stream (`optuna_loop.py freeze`: 640 record ids stratified by source with the mixture weights;
   sha in `trial_stream_sha`) for 1 warm-up step + 4 timed steps, so all trials time the same records.
   **Guards are now comparable across trials:** the quality guard compares the probe-loss drop after the same warm-up
   optimizer step(s), on the same 32-sample batches, against the round-3 baseline. Quality checkpoints
   (`validate-plan`, PROFILE=optuna_validate) train best vs baseline for 150 optimizer steps and compare val
   acc / nll / ece on a frozen, stratified ~400-record val set (accept if nll <= base + 0.05 and acc >= base - 1 pt;
   with ~400 records the acc standard error is ~2 pt). Expected: importances that show real techniques, and a TPE that
   no longer chases batch size. Open: `max_state_tokens` is still sampled and changes sequence lengths and quality the
   same way; `ple_cpu` is PENDING a paired test (enqueue the baseline with ple_cpu 0 and 1). Round 2 note: every r2
   trial ran ple_cpu=1 (sample: false dims were not written into trials.json, and train_prism defaults to 1).

## Ideas (round 4 → round 5)

Round-4 facts (kernel v6, one reload group, ple_cpu=1, fp16, mb 8 × accum 4): baseline 0.825 samples/s (1.21 s/sample,
peak 8.3 GB); chunked_math 0.829 and sdpa_bool 0.830 are within ~0.6% (noise); chunked_math + grad_ckpt off is
infeasible at mb 8 (OOM at 13.9 GB). **pad_frac 0.52**: half of the tokens in every micro-batch are padding. Profile
(2 steps, CUDA time): mm 28%, mul 15%, efficient-attention bwd 13% + fwd 7%, copy_ 12.5%, "Command Buffer Full" 10.6%,
PLE CPU lookup ~1% of CPU. The micro-batch-16 probe fits (13.1 GB of 14.56).

6. **Packing on vs off, then length-grouped micro-batches (OJ-060).** Hypothesis: with pad_frac 0.52 about half of all
   matmul and attention work is on padding. `packing` / `pack_len` / `option_subsample_k` are implemented since 2b642a0,
   so round 5 can enqueue `packing=on` against the baseline directly. A cheaper variant: sort each global batch of 32 by
   length into its 4 micro-batches; the optimizer step stays identical (same 32 samples), only padding changes.
   Expected: up to ~1.5–1.9× samples/s at equal quality. References: Krell et al. 2021, *Efficient Sequence Packing
   without Cross-contamination*, arXiv:2107.02027; HF Trainer `group_by_length` (LengthGroupedSampler).
7. **micro_batch 16, grad_accum 2 (same global batch 32).** Hypothesis: the round-4 diag shows mb 16 fits (13.1 GB) with
   ple_cpu=1 + grad-ckpt; the optimizer step is unchanged, while each GEMM gets twice the rows (larger M), which raises
   arithmetic intensity on the T4 tensor cores. ("Command Buffer Full" in the profile means the CPU waits on a full
   launch queue, i.e. the GPU is the bottleneck, not launch overhead.) Needs a new round (micro_batch is a round
   constant). Reference: NVIDIA, *Deep Learning Performance Guide: matrix multiplication background* (larger GEMM
   M dimension raises arithmetic intensity), https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/
8. **Fuse the elementwise ops (mul 15% + copy_ 12.5% + add ~7%).** Hypothesis: RMSNorm, GeGLU, the LoRA scaling and the
   fp16/fp32 casts are memory-bound elementwise kernels; fused Triton kernels (Liger) or `torch.compile` of the decoder
   layer cut them. Expected: 10–20%. References: Hsu et al. 2024, *Liger Kernel*, arXiv:2410.10989; Ansel et al. 2024,
   *PyTorch 2* (torch.compile), ASPLOS.

## Length curriculum (user idea; code ready, not benched)

**Idea.** Train short requests first, then longer ones: stages 128, 256, 512, 1024, 2048 tokens. Requests are
**bucketed** by their natural encoded length (state + questions + options + flags, exactly what `prism_collate`
builds at `max_state_tokens`), never cut or split to fit a stage. A request longer than the last stage trains in
the last stage, in a row of its own. Reference: Li, Zhang, He 2022, *The Stability-Efficiency Dilemma:
Investigating Sequence Length Warmup for Training GPT Models*, NeurIPS 2022, arXiv:2108.06084. That paper
**truncates** sequences early in GPT pre-training, over a short warm-up. Here we bucket instead, because a cut
request loses evidence and is no longer a Jev request. So the paper supports "short first" only loosely.

**Code.**
- `openjev/packing.py`: `request_lengths`, `stage_of`, `curriculum_order`, `CurriculumStream`, `build_curriculum`,
  `scan_parts`, `bucket_table`, `freeze_stages`.
- `train_prism --length-curriculum on --curriculum-stages 128,256,512,1024,2048 --curriculum-pack-mult 1`. The run's
  pool is steps × bs × grad_accum records drawn like the Mixture (alpha weights), so the source mix stays the
  Mixture's. One epoch is that pool, every record exactly once, stages in increasing length. Each stage's share of
  the steps therefore equals its share of the records. Each micro-batch packs at mult × the stage max of its longest
  record, or stays unpacked with `--packing off` (length-bucketed). `off` (the default) keeps the Mixture path
  unchanged.
- `tools/length_curriculum.py measure | freeze | space`.
- `bench_trials.py --stage-streams` with trial params `length_stage` (0 = the mixed curriculum-off reference) and
  `stage_pack_mult` (0 = unpacked, 1 = pack at stage max, 2 = pack at 2× stage max).
- `PROFILE=optuna_length` (kernel `openjev-prism-length`) in `kaggle/prism/{entry.py,build.sh}`.
- Tests: `tests/test_length_curriculum.py`.

- **max_state 1024 vs 2048:** the stage counts are identical except for 1 helpsteer3 record that is longer than
  2048 at max_state 2048 (it would train in the last stage, alone in its row). At 1024, 12,939 states are cut, and
  the cut helpsteer3 records still land in ≤2048 (template + 1024 > 1024). At 2048 only 1 state is cut. In the
  frozen stream, the ≤2048 stage has p50 1,122 and max 1,122 tokens at max_state 1024; at 2048 it has p50 1,125,
  p95 1,244, max 1,379. The 2048 stage has enough records (20,825; 6.6% of steps), so it is included. The bench runs
  at max_state 1024, because the yaml `max_state_tokens` choices stop at 1024 and choices must not change. A 2048
  stage with real 2048 states needs OJ-067 and a new dimension; its cost will be somewhat higher than these numbers.
- **The buckets are almost the sources.** ≤128 is 97% prm800k. ≤256 is mostly prm800k, then lichess and
  diplomacy. **banking77 and clinc150 sit 100% in ≤1024** (their 77 and 150 options make the template long).
  **≤2048 is only helpsteer3.** So the curriculum is in effect a source-ordered curriculum: intent classification
  first appears after ~74% of the steps, and helpsteer3 is mostly in the last 6.6%. That risks forgetting the early
  sources and under-training the late ones. Option sub-sampling (OJ-072, banking77/clinc150 ~1000 → ~200 tokens)
  would move those two sources to ≤256 and change the table.

**Packed at the stage max = unpacked.** Every record in a power-of-two bucket is longer than half the bucket
(except a few in ≤128), so first-fit-decreasing at pack_len = stage max puts one request per row. This was checked
exactly on the frozen stage streams (the 96 records the bench times, micro-batch 8): 8.00 rows per micro-batch and
the same padded tokens for `stage_pack_mult` 1 and 0, in every stage. So the coordinator's (a) "packed at bucket
pack_len" and (b) "length-bucketed unpacked" have the same layout, and only (b) is benched (stage_pack_mult 0).
The other candidate is 2× the stage max (stage_pack_mult 2).

## Fixed multi-length bench set (study openjev-speed-v3, round 7; user decision 2026-11-23)

**Decision (user):** "1024 or 2048 anything is bad! make a dataset of various 128/256/512/1024/2048 and fix this
dataset (a small one though)". No more single pack_len as a trial condition. From round 7 every speed trial runs

study `openjev-speed-v3` in the same `runs/optuna/study.db`; rounds 3-6 stay in `openjev-speed-v2` (not

**Trial protocol** (`bench_trials.py --bench-lengths`, fixed micro-batch 8, global batch 32, fp16, ple_cpu 1,
grad_ckpt on): probe loss; 1 shared warm-up optimizer step = one micro-batch from each of ≤2048, ≤1024, ≤512, ≤256
(longest first, so the allocator reaches the peak shape first); probe loss (the quality guard); then each bucket
in turn (128 → 2048): 1 timed optimizer step = that bucket's 32 records as 4 micro-batches of 8 (length-grouped,
unpacked: inside a bucket, packing at the bucket max = unpacked). Per bucket: samples/s, tokens/s, padded
tokens/s, pad_frac, peak GB (`buckets` attr). Objective `samples_per_sec` = 1 / Σ_b w_b × (s per sample in b) —
the time a training-like mix of samples takes (`packing.mix_objective`). OOM in any bucket = PRUNED
`infeasible_at_mb8` (the mix is undefined without every bucket). max_state_tokens = 2048 from the file (overrides
the param; recorded as `max_state_tokens_used`); packing / pack_len are ignored by the bench and dropped from the
fixed conditions (`bench_set_sha` instead); they stay train_prism flags.

**Timing budget (T4).** The request was 5 buckets × (1 warm-up + 2 timed steps) = 15 optimizer steps × 32 records
(the 32-record buckets would wrap 3x). At ~720 padded tokens/s (r6 trials 27-31) that is ~1.1 s per padded
1k tokens: 3 × 95.5k padded tokens ≈ 400 s timed+warm-up, ~7 min per trial. **Cut:** 1 shared warm-up step
(~22.5k padded tokens, ~31 s) + 1 timed step per bucket (95.5k padded tokens, ~133 s: ≤128 ~6 s, ≤256 ~11 s, ≤512
~21 s, ≤1024 ~38 s, ≤2048 ~56 s) + 3 probe passes (~10 s) ≈ **~175 s ≈ 3 min** per trial (estimate; the ≤2048
bucket may be slower per token). `timed_steps: 2` in the yaml restores 2 timed steps per bucket (~5 min).
Each timed step averages 4 micro-batches, so the per-bucket number is not a single forward.

**Length-grouped training batches (user addition, SO "PyTorch: can I group batches by length?").**
`train_prism --length-grouping on|off` (default **on**; off with --length-curriculum, which already groups;
both on = error), `--group-chunk 50`: `packing.LengthGroupedStream` takes 50 × bs records of the Mixture, sorts
them by encoded length, cuts micro-batches of bs and shuffles their order (seeded; the same stream on every DDP
rank, takes stay aligned to bs so the rank shards are whole grouped micro-batches). Every record of a chunk is
served exactly once; not a curriculum. pad_frac of one pass over the whole train set (403,008 records, each once,
micro-batch 8, `tools/length_curriculum.py pad`):

| batching | pad_frac @ max_state 1024 | @ 2048 | rows / mb |
|---|---:|---:|---:|
| random | 50.3% | 50.8% | 8.00 |
| length-grouped (chunks of 50 mbs) | **3.1%** | 3.4% | 8.00 |
| random + packed 1024 | 17.8% | 18.6% | 3.71 |
| length-grouped + packed 1024 | 7.1% | 7.4% | 3.92 |

Grouping alone pads less than packing at 1024, and packing grouped micro-batches pads MORE (rows of similar-length
records fill 1024 unevenly). train_prism's `--packing` default is still `on` (1024): with grouping on, `--packing
off` is the likely better training setting, to be confirmed on GPU.

**Round 7 enqueue** (`kaggle/prism/r7_enqueue.json`, `propose --n 0 --enqueue-json "$(cat
kaggle/prism/r7_enqueue.json)"`): trial 0 = the round baseline (yaml defaults, 1 GPU, auto-enqueued), DDP (2×T4,
all-reduce per step), local SGD K=50. A trial has only 6 optimizer steps, so K=50 never averages inside the timed
loop: local SGD here measures 2-rank speed without sync (the upper bound for DDP). Not pushed to Kaggle.
